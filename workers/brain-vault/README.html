Brain Vault

TAHA Studio Labs Growth Department V1. Phase 1: the Vault foundation. Phase 2: the client portal at /grow/. Phase 3: the Growth Clients panel inside ScriptForge. Phase 4: the Business Brain. Phase 5: the Campaign Generator. Phase 6: GDPR tools and the handover (see HANDOVER.html). Branches growth-phase-1 (the Worker deploys from it) and main (the website), folder workers/brain-vault/.

The Brain Vault is a Cloudflare Worker that both sides talk to: the client onboarding portal (phase 2) and the Growth Clients panel in ScriptForge (phase 3). It runs on Cloudflare all the time, so you have nothing to start or restart. Phase 1 builds the foundation: the database, file storage, the three data contracts (JSON Schemas), magic link login with the client and admin roles, the invite email and the rate limits.

House rules built into the code: no em-dashes in any text the Vault produces. No endpoint accepts an AI API key, and none is ever stored or logged. No client business content goes into logs or emails. Public ScriptForge users see nothing new, and the Vault answers them with "not signed in".

2. Endpoints in phase 1

All of them sit under https://tahastudiolabs.com/api/vault.

Method and pathWhoDoes
POST /auth/request-linkAnyoneBody {"email","lang"}. Sends a link only to invited clients and admin emails. The answer is always the same neutral message. Limited to 5 per email and 20 per IP each hour.
GET /auth/verifyEmail linkOpens the confirmation page. The token is in the #t= part of the link, so it never reaches server logs.
POST /auth/verifyConfirmation pageUses up the token, sets the 30 day session cookie, and returns where to go for the role.
GET /auth/meSigned inReturns the role, the email, how you signed in (vault or scriptforge) and, for a client, its own record and status.
POST /auth/logoutSigned inEnds the Vault session.
POST /admin/clientsAdminBody {"name","email","language"}. Creates the client with status Invited and sends the bilingual invite.
GET /admin/clientsAdminLists clients with status, last login, latest intake and brain versions, and the "new intake" flag for phase 3.
POST /admin/clients/:id/inviteAdminSends the invite again with a fresh link.
GET /schemas/intake|brain|campaignAnyoneThe contract files, so the portal and ScriptForge validate against the same copy.
GET /healthAnyoneShows whether D1 and R2 are connected. It holds no data.
GET /consoleAnyoneThe phase 1 test console.

The rest of the endpoints in spec section 4 (consent, intake, uploads, status, brain, campaign, erasure) arrive in the phase that needs them. The tables they use already exist.

2b. Endpoints added in phase 2

All under /api/vault, client role only unless noted. A client can only ever reach its own record.

Method and pathDoes

3. How login works

  1. Someone enters an email. If it belongs to an invited client or is in ADMIN_EMAILS, the Vault creates a random 32-byte token, stores only its SHA-256 hash, and emails the link. Any other email gets the same message and no email. The work happens after the reply is sent, so the reply takes the same time for every email.
  2. The link opens /api/vault/auth/verify#t=.... The person clicks Logga in / Sign in once. This extra click is deliberate: Outlook and Gmail scanners open links automatically, and without it they would use up the one-time link before the person ever saw it.
  3. The token gets marked as used in one database step, so a second click always fails. It also stops working after 15 minutes.
  4. The Vault sets the cookie __Host-tv_session, which is HttpOnly, Secure, SameSite=Lax and lasts 30 days. Only its hash is stored.
  5. Clients land on CLIENT_HOME and admins on ADMIN_HOME. In phase 2, CLIENT_HOME became the portal. In phase 3, ADMIN_HOME became /scriptforge/#growth, so an admin magic link opens the Growth Clients panel. The phase 1 test console still works at /api/vault/console.

Admin role: two ways in

A. Magic link, exactly like a client. B. ScriptForge's existing Sign in. If there is no Vault session, the Vault asks ScriptForge's own /api/me who is signed in (it forwards the browser's cookies). If that email is in ADMIN_EMAILS, you are admin. The Vault holds no Supabase keys. ScriptForge's device limit and sign out still apply. Nobody can become a client this way, and a normal ScriptForge user gets nothing. To turn this path off, set SCRIPTFORGE_ADMIN_BRIDGE to off.

7. Interpretations of the spec, for Harry to confirm

  • One click on the verify page. The spec says GET /auth/verify validates the token. Here, the GET shows the page and a click does a POST to finish, for the scanner reason in section 3.
  • Email through Gmail for now. Resend cannot send as a @gmail.com address, so Gmail SMTP with an app password is the default until hej@tahastudiolabs.com exists. Gmail is not an EU data region, but these emails carry only names and links. Resend in the EU region is ready to switch on.
  • Schema details the spec left open: landingPage.benefits is three {title, text} blocks, and landingPage.faq holds {q, a} rows. A draft intake has intakeVersion 0 and submittedAt null. The required fields for submit are listed in x-requiredOnSubmit and are checked at submit time, so drafts can be half filled. website takes free text, because the pilot client only has Instagram. Counts are fixed to match the spec: 5 hooks, 5 ad variations, 3 CTAs, 2 email subjects. googleBusinessPost.ctaType is one of BOOK, ORDER, SHOP, LEARN_MORE, SIGN_UP or CALL. Field names are exactly as in the spec.
  • Portal address. Spec section 3 says /growth/ and section 10 says /grow/. Phase 1 does not depend on it, and it becomes the value of CLIENT_HOME in phase 2.
  • wrangler.json instead of wrangler.toml, and migrations in JavaScript, so that every file in the archive is HTML, JS or JSON.
  • G1: two extra brief fields. Next to the spec's list, each brief has subject (product, place, team, people, mood, offer_background), so the client photo rule can be enforced in code, and cast (who appears, from the brain). For Swedish and English campaigns, overlay_alt holds the English overlay. A missing photo is source: client_photo with photo_ref: null.
  • G1: ScriptForge fixes the sizes. The model never chooses a size or clear zone: ScriptForge decides which outputs need a brief and copies the size from platforms.json. Google Business and email posts in the social copy share the brief of their own output. Ads take the size of the first paid channel picked (Facebook, then Instagram, LinkedIn, TikTok). The video gets a 9:16 cover, plus a TikTok cover when TikTok is a channel.
  • G1: finished images are their own table, not the files table. The spec says the files table gains a delivery section in Part B. Changing that table's allowed sections needs a table rebuild in SQLite, so G1 adds a deliveries table (which the spec also lists for Part B) and stores the images there. Part B can show them directly.
  • G1: brand kit stored per client. The brain has no colours or logo, so the panel keeps a small brand kit per client in the Vault, imported from the brand.json in D:\BRAND-KITS or typed in. G2 landing pages will use the same record.
  • G1 live fix (6 Oct 2026): briefs in batches. On the live site one call for 16 briefs ran past Cloudflare's 100 second limit on the relay (HTTP 524). Make visuals now asks for four briefs per call (batchSize and batchMaxTokens in visuals.prompt.json), checks and retries each batch on its own, and tries once more by itself after a timeout or a 5xx answer.
